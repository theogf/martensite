martensite Architecture

How Helix, jld, and a live Julia REPL fit together.

Two paths into one session
                       paste path  (send-*)
Helix ──► jld eval-repl ──[repl.sock]──► REPL tty buffer ──► your terminal
                                          bracketed paste, ans set

                       capture path  (eval-*)
Helix ──► jld eval ─────[daemon.sock]──► eval in Main ────► Helix popup
                                          prompt untouched

Agents ─► jld --id=<id> eval ────────────► same Main, captured output

Both paths reach the same Main. They differ only in who evaluates the code and therefore where the result comes out. There is no daemon of our own in this picture: jld owns process lifetime, and martensite is a single Steel file that shells out to it.

1

Resolving the session

Entry point: resolve-session — martensite.scm

A daemon's identity is project + name. jld derives the project itself by walking up from the subprocess working directory (inherited from Helix) looking for a Project.toml, so the plugin only has to supply the name — which exists to disambiguate several sessions on one project.

  • 1st MARTENSITE_SESSION, then JLD_NAME — the latter is jld's own override, honored here too so that one variable set in a layout names the session on both sides at once.
  • 2nd First line of a .juliasession file in the project root — a name that survives renaming the tab.
  • 3rd Zellij tab name, then tmux window name — probed by running zellij action current-tab-info / tmux display-message, gated on ZELLIJ / TMUX being set. Zellij reports several key: value lines, so the first line is taken before splitting on ": ".

Falling through all of those yields repl, which is what JuliaDaemon.serve() picks with no arguments. Note that a spawned daemon's default name is the empty string, a different id entirely — so the name is always passed explicitly rather than omitted.

2

The paste path — send-*

jld eval-repl connects to repl.sock, served by the REPL process itself (JuliaDaemon/src/repl_input.jl).

  1. Stash any half-typed input out of the LineEdit buffer, so the paste cannot splice into what the developer is mid-way through typing.
  2. Inject the code into stdin's buffer wrapped in bracketed-paste markers (ESC[200~ … ESC[201~), then notify the tty condition variable.
  3. LineEdit cannot tell it from a real terminal paste: the code is echoed at the prompt, evaluated by the REPL, ans is set, and the prompt is redrawn.
  4. Restore the stashed input at the fresh prompt. Ordering is guaranteed by byte order in the tty buffer.

Because the REPL owns the evaluation, its output goes to the developer's terminal. The socket acknowledges the paste and nothing more, so this path cannot populate the popup.

3

The capture path — eval-*

Entry point: run-jld — martensite.scm

  1. Spawn jld --name=<session> --max-output=16k eval <code> with both stdout and stderr piped. Piping stderr is not optional: Julia writes errors and stacktraces there, and an unpiped stderr is inherited from Helix's own process — it writes raw text straight to the terminal, bypassing the TUI compositor and the popup entirely.
  2. Read both port handles before waiting. wait->stdout consumes the whole child handle internally, leaving nothing to pull stderr from afterwards.
  3. Unwrap the exit status. Steel's wait returns a Result, not a bare integer — comparing it to 0 directly is silently always false.
ExitMeaningPlugin response
0evaluatedpopup with the result
1Julia errorpopup with the stacktrace
3daemon unreachable, or no REPL attachedfall back to a captured eval

Rendering the popup

Entry point: show-output! — martensite.scm

  1. Captured text is fed to a real VTE (steel-pty's raw-virtual-terminal) rather than being rendered as markdown, so the terminal emulator does its own line-wrapping and would interpret SGR codes if any arrived.
  2. Newlines are rewritten to CRLF first. The output is piped, not a pty, so there is no kernel tty driver to translate them; a faithful VTE treats a bare \n as a linefeed only, and every line after the first would staircase to the right.
  3. The VTE is 300 rows tall, far more than the popup shows. Sized to the visible rows it would scroll like a real terminal as it is fed, showing the tail of a long stacktrace and cutting off the ERROR: line at the top — which is the useful part. The render step windows it back down.
  4. The box is anchored below the cursor, clamped into the editor area, and dismissed on the next key event.
5

Agents sharing the session

This is the property the whole design exists to protect: an agent reuses the developer's warm session without disturbing their work.

CommandEffect on the developer
jld --id=<id> eval None. Output is captured to the agent; the prompt is never touched.
--scratch Evaluates in a throwaway module that sees Main's bindings but cannot clobber them.
--module=M A persistent agent namespace beside Main.
--name=<unique> A wholly separate daemon, when sharing is not wanted at all.
jld transcript Reads what the developer has been doing, for context.
!

Known gaps

Both live upstream in JuliaDaemon.jl, and both are small.

  1. eval-repl never returns the result. cmd_eval_repl reads back only a done frame, so the paste path has nothing to show in a popup. Making the socket wait for the evaluation and return its captured output would close this.
  2. jld eval output is always monochrome. The wire protocol already carries a color field, threaded all the way into the result and error renderers — but only the attached-REPL client ever sets it, and there is no CLI flag. The daemon side is built; only a client flag is missing.
