Conductor / Client Architecture

How juliaclient and julia-conductor cooperate to route Julia REPL sessions.

Lifecycle overview
juliaclient  ──[conductor.sock]──►  conductor  ──[wsetup.sock]──►  Julia worker

                     ◄──[4 socket paths]──
juliaclient  ──[stdin / stdout / stderr / signals]────────────────► Julia worker
1

Client connects to conductor

Entry point: juliaclient::main — client/src/main.rs:733

  1. Scan env — compute an XOR fingerprint over all environment variables (scan_env, line 34). Used as a cache key so the conductor avoids requesting the full env on repeated calls from the same shell.
  2. Connect to the conductor's socket (Unix domain or TCP). If the first attempt fails, signal the conductor via its PID file to recreate the socket, then retry (connect_to_conductor, line 260).
  3. Send handshake (send_client_info, line 344): magic 0x4A444301, flags (tty?), pid, ppid, cwd, env fingerprint, argv.
  4. Conditional env dump — if the conductor responds with ENV_REQUEST (0x3F), send the full env key/value list, then continue reading (receive_worker_sockets, line 426).
  5. Receive 4 socket paths — stdin, stdout, stderr, signals — returned as length-prefixed strings.
  6. Connect to all four sockets directly on the Julia worker process.
2

Conductor dispatches the request

Entry point: Conductor::handle_client — conductor/src/conductor.rs:250

  1. Read request — flags, pid, ppid, cwd, env fingerprint, raw argv.
  2. Resolve env — check EnvCache by fingerprint. On a miss, send ENV_REQUEST, receive the full dump, cache it.
  3. Parse args and resolve the Julia project path.
  4. Compute worker key — a string that identifies which pool to draw from. For a normal run: project_path\0julia_channel. Sandboxed variants use a different prefix (__sandbox__ / __lsandbox__).
  5. Select or spawn a worker using the priority logic below.
  6. Call worker.run_client(info) — sends ClientRun over the control socket and blocks waiting for a Sockets reply.
  7. Send the 4 socket paths back to the client.

Worker selection priority

  • 1st Session label match — if --session=label was passed and a worker carries that label, always route to it.
  • 2nd PPID affinity — a worker that previously served the same parent shell PID is preferred, so a terminal session keeps hitting the same Julia process.
  • 3rd Second-most-recently-active available worker — the freshest available worker is intentionally skipped to act as a warm standby.
3

Worker spawning

Entry point: Worker::spawn_impl — conductor/src/worker.rs:112

  1. Create a temporary socket wsetup.sock in the runtime dir.
  2. Launch Julia: julia --eval "using DaemonWorker; DaemonWorker.runworker(setup_path, id, conductor_path)". The worker is placed in its own process group (setpgid) so terminal SIGINT doesn't propagate to it.
  3. Block on setup_listener.accept(). Julia's DaemonWorker.runworker connects back on startup, signalling it is ready.
  4. Delete the setup socket, send WORKER_MAGIC (0x4A445701), and store the stream as the worker's long-lived control socket.
  5. For sandboxed workers (Linux only) the same flow runs inside an unprivileged user namespace created via raw unshare/pivot_root/bind mount syscalls — no root required.
4

Worker accepts the client

When the conductor sends ClientRun, DaemonWorker.jl creates 4 new sockets — one each for stdin, stdout, stderr, and signals — and returns their paths (Unix socket paths, or host:port in TCP mode) in a Sockets reply.

The worker then blocks accepting connections on those four sockets, waiting for the client to arrive. Once all four are connected, I/O can flow.

5

I/O proxying

Entry point: run_event_loop — client/src/main.rs:616

A poll() loop over four file descriptors:

FDDirectionNotes
stdin → worker stdin Raw bytes forwarded. In --sync mode without raw terminal, CookedState provides client-side line editing with local echo before sending.
worker stdout → terminal stdout Straight byte copy.
worker stderr → terminal stderr Straight byte copy.
signals socket bidirectional Typed message channel — see signal table below. Loop exits when SIG_EXIT is received and both stdout and stderr have reached EOF.

Signal messages

IDNameDescription
0x01 SIG_EXIT Worker sends exit code; client tears down and exits.
0x02 SIG_RAW_MODE Worker requests raw / cooked terminal mode. Client acks with same ID.
0x03 SIG_QUERY_SIZE Worker asks for terminal dimensions. Client replies with rows + cols.
0x04 SIG_NODELAY Request TCP_NODELAY on the socket.

SIGINT forwarding — the client installs a custom SIGINT handler that writes a raw \x03 byte onto the worker's stdin socket (line 587) instead of raising the signal locally. This lets Ctrl-C reach Julia's REPL interrupt handler correctly even when the terminal is in raw mode.

6

Teardown

  1. Restore terminal to cooked mode (set_raw_mode(false)).
  2. Send a ClientExit notification to the conductor (notify_exit, line 559): magic 0x4A444E01, type 0x04, client pid.
  3. The conductor's accept loop recognises the notification magic and routes it to handle_notification, which decrements the worker's active_clients count and optionally runs a health-check ping.
  4. Exit with the code received from SIG_EXIT.
∞

Background health checks

A background thread calls Conductor::check_workers periodically. For each idle worker whose last-ping timestamp is older than ping_interval:

  1. Send Ping on the control socket; wait up to ping_timeout for a Pong.
  2. On timeout or error: kill the worker (SIGKILL) and remove it from the pool.
  3. On Pong: compare the worker's self-reported active-client count with the conductor's count. If they diverge, send SyncClients with the conductor's PID list so the worker can reconcile.

The conductor also maintains a reserve worker — a pre-warmed Julia process that is assigned to the first incoming client that doesn't need an interactive session, eliminating Julia startup latency. Once consumed, a new reserve is spawned immediately.
